Fixing Abel et al.'s kernels

The comparison sweep found nine problems in the GPU kernels. Each fix is a switch on the branch sweep-fixes (on top of commit 15ce37d of yipihey/GLMMHDTurb, not yet public). Three jobs on Sherlock's H100s ran every fix beside the original kernel and, for the shocks, against the AthenaK 4096² reference. How they were run: sherlock_fixes/README.md; the shock scores: scripts/fix_accuracy.py.

1. Float16 storage had too few digits

fixedintegrator_plm!, integrator_plm_ppm!
Problem

The fast production kernel keeps its working data in Float16, about 3 significant digits. On a fine grid, neighbouring cells of a smooth wave differ by less than Float16 can resolve, so slopes become rounding noise and the error grows as the grid gets finer.

Fix

Each tile of cells keeps one reference value in Float32 and stores every cell as "value minus reference" in Float16, so small differences keep all 3 digits. Every GPU block uses the same references, so a face shared by two blocks gets the same flux from both and conservation stays exact. On by default; anchored=false gives the original.

2. Float16 overflowed on strong flows

partly fixedsame kernels
Problem

Float16 can't hold numbers above 65,504. On magnetised blasts some fluxes went past that and became infinity.

Fix

Fluxes are stored as (dt/dx)·F, how much a cell changes in one step, which stays far below 65,504, split into a Float16 head and tail (about 7 digits together).

3. The CT prototype was only first order

fixedct_mhd.jl
Problem
  • Half the slope. pslope returned half the limited slope and its caller halved it again: each face got a quarter of the cell-to-cell difference instead of half.
  • Predictor in one direction. The half step of each cell used only the flux along the face's own direction. In 2D and 3D it needs all of them, as the GLM kernels already do.
Fix
- pslope(L,M,R) = 0.5f0*moncen(M-L, R-M)
+ pslope(L,M,R) =      moncen(M-L, R-M)
- hanc1d(...)   # half step with the face's own flux only
+ hanc3d(...)   # half step with the x, y and z fluxes

4. HLLD crashed where the field crosses a face

partly fixedhlld_x
Problem

HLLD divides by a quantity that becomes zero when the field points straight through a cell face. The check for "is it zero?" used 10⁻¹², but single-precision rounding leaves about 10⁻⁷, so the check never fired.

Fix
- small = abs(denK) < 1.0f-12
+ small = abs(denK) < 1.0f-4*pts      # relative to the face pressure

5. The cleaning speed jumped on short steps

fixedevery step_* function
Problem

c_h = Courant · dx / (3 · dt) used the step actually taken. The last step before each output is shortened to land on the output time; a step 1,000× shorter made c_h 1,000× larger for that step.

Fix

Each step function takes the normal step as dt_cfl and computes c_h from it. Code that doesn't pass it behaves as before.

Result

Fixed with no side effects: the fixed LLF kernel matches the original on every test (same steps, shock errors ratio 0.99–1.00, same speed, 2.03 billion per second).

6. GLM cleaning leaked field into a field-free region

fixedstep_plm!(…; fct=true)
Problem

In the Kelvin–Helmholtz test with the field confined to one layer, GLM let field into the field-free vortex: 27× the reference amount at 256². No setting of the cleaning fixes that.

Fix

A new option replaces GLM with constrained transport on the cell-centred field (Tóth 2000): B is updated from edge electric fields, which keeps ∇·B at the cell corners at rounding level. No ψ, no c_h.

Cost

Float16: 1.17 billion per second (1.82 on the 6-cell tile). Float32: 1.55. Needs 9 extra numbers per cell.

The fixed CT prototype gets worse on the finest grid. Both CT schemes build their edge electric fields as a plain average of face fluxes, which is known to fail this test (Gardiner & Stone 2005). The old half slope smoothed that away; the sharp scheme exposes it.

Next fix: an upwinded edge average (Gardiner & Stone's), in both CT schemes.

9. "Fixes off" matches the original to rounding, not to the last digit

found, not fixed
Result
  • LLF kernel: identical to the sweep in all 21 outputs × 35 columns, on the entropy wave and Orszag–Tang.
  • Production kernel: identical on the entropy wave.
  • Production kernel on Orszag–Tang, and PPM: same number of steps, total energy within 3 × 10⁻⁸, kinetic and magnetic energy within 3 × 10⁻⁶, shock errors equal to 3 digits.

The differences appear only where ψ is not zero (on the entropy wave it stays zero), so the GPU compiler arranges some cleaning arithmetic differently in the larger kernel. The sweep's own repeated runs match each other exactly, so it is not the GPU.

Harmless for results. An exact match would need the original kernel kept as a separate function on the branch.

What we would recommend

On power-of-two grids, the Float32 4-cell tile: as fast as Float16 there, as accurate as the fixed Float16 kernel up to 256 (less at 512), and it survives Mach 9. On grids divisible by 6, the fixed Float16 6-cell tile is the fastest accurate kernel (1.91 billion per second). Constrained transport where leakage matters, once its field loop is fixed. Courant 0.25–0.3 in 3D.
