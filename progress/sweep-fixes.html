Fixing Abel et al.'s kernels

The comparison sweep found problems in the GPU kernels. Below is every change the branch sweep-fixes makes to the original code (on top of commit 15ce37d of yipihey/GLMMHDTurb; the branch is public in the fork Solaceonx/GLMMHDTurb), with the problem it addresses and the result. The last section lists the changes by commit and function. Three jobs on Sherlock's H100s ran every fix beside the original kernel and, for the shocks, against the AthenaK 4096² reference. A fourth reran the five fixed kernels on every test of the sweep at every grid and seed: 700 runs, results below. How they were run: sherlock_fixes/README.md; the shock scores: scripts/fix_accuracy.py.

1. Float16 storage had too few digits

fixedintegrator_plm!, integrator_plm_ppm!
Problem

The kernel works on one tile of cells at a time (6×6×6 plus a 2-cell border), and the tile must fit in the GPU's 48 KB of fast memory. In Float32 (about 7 digits) a 6-cell tile needs 90 KB; in Float16 (about 3 digits) it needs 45 KB. So the kernel stores the cell values, the face values and the face fluxes in Float16.

Three digits are too few for smooth flows on fine grids. Example: the entropy wave has density near 1.0 with a wiggle of 0.2. On a 512 grid two neighbouring cells differ by about 0.002, but near 1.0 Float16 stores numbers in steps of about 0.001. The slope between neighbours, which the scheme uses, comes out 20–40% wrong. Finer grids make the differences smaller but not the steps, so the error grew as the grid got finer.

Fix
  • Store the difference, not the value. Each tile keeps one reference value, the state of its first cell, in Float32. Every cell is stored as "value minus reference" in Float16. In a smooth flow those differences are small, so Float16's 3 digits go to the part that matters. Reading a value adds the reference back in Float32.
  • Same reference everywhere, so conservation stays exact. A face between two tiles is computed twice, once by each tile's GPU block. A cell always uses the reference of the tile it belongs to, whichever block reads it (each block loads the references of the 27 tiles around it). Both blocks decode it identically and compute the identical flux, so no mass leaks.
  • On by default with Float16; anchored=false gives the original storage.

2. Float16 overflowed on strong flows

partly fixedsame kernels
Problem

Float16 can't hold numbers above 65,504; larger values become infinity. On the strong magnetised blast the flux of ψ (c_h² B) reached about 130,000, turned into infinity, and the run died at the first output.

Fix
  • Store the change, not the flux. Instead of the flux F, the kernel stores (dt/dx)·F: how much that face changes the cell in one time step. The time step keeps nothing moving more than a fraction of a cell per step, so this is always a modest number; the ψ flux that reached 130,000 becomes a number of order 1 to 10. The update then simply adds these stored changes.
  • Seven digits for the flux. Fluxes go straight into the update, so 3 digits aren't enough for them either. Each is stored as two Float16 numbers: a head (the value rounded to Float16) and a tail (what that rounding lost). Together they hold about 7 digits, like Float32. This needs no extra memory: once the fluxes are computed the face-value arrays are free, so the head goes into one and the tail into the other.
  • Together with fix 5, c_h comes from the normal time step, so a step shortened to land on an output no longer inflates the ψ flux.

Fixed except at Mach 9. Inside a strong shock, cells of one tile differ by large factors, so "value minus reference" is as big as the value and storage is back to 3 digits; most likely the pressure, tiny next to the kinetic energy at Mach 9, is lost in that rounding and goes negative (not yet proven). The Float32 tile survives Mach 9, and on power-of-two grids it is as fast as Float16 (1.63 against 1.61 billion per second, same GPU).

Cost of fixes 1 and 2 together: about 29% slower. Each block loads 27 references, does an extra add per value and writes two numbers per flux.

3. The CT prototype was only first order

fixedct_mhd.jl
Problem
  • Half the slope. pslope returned half the limited slope and its caller halved it again: each face got a quarter of the cell-to-cell difference instead of half.
  • Predictor in one direction. The half step of each cell used only the flux along the face's own direction. In 2D and 3D it needs all of them, as the GLM kernels already do.
Fix
- pslope(L,M,R) = 0.5f0*moncen(M-L, R-M)
+ pslope(L,M,R) =      moncen(M-L, R-M)
- hanc1d(...)   # half step with the face's own flux only
+ hanc3d(...)   # half step with the x, y and z fluxes

4. HLLD crashed where the field crosses a face

partly fixedhlld_x
Problem

HLLD divides by a quantity that becomes zero when the field points straight through a cell face. The check for "is it zero?" used 10⁻¹², but single-precision rounding leaves about 10⁻⁷, so the check never fired.

Fix
- small = abs(denK) < 1.0f-12
+ small = abs(denK) < 1.0f-4*pts      # relative to the face pressure

5. The cleaning speed jumped on short steps

fixedevery step_* function
Problem

c_h = Courant · dx / (3 · dt) used the step actually taken. The last step before each output is shortened to land on the output time; a step 1,000× shorter made c_h 1,000× larger for that step.

Fix

Each step function takes the normal step as dt_cfl and computes c_h from it. Code that doesn't pass it behaves as before.

Result

Fixed with no side effects: the fixed LLF kernel matches the original on every test (same steps, shock errors ratio 0.99–1.00, same speed, 2.03 billion per second).

6. GLM cleaning leaked field into a field-free region

fixedstep_plm!(…; fct=true)
Problem

In the Kelvin–Helmholtz test with the field confined to one layer, GLM let field into the field-free vortex: 27× the reference amount at 256². No setting of the cleaning fixes that.

Fix

A new option replaces GLM with constrained transport on the cell-centred field (Tóth 2000): B is updated from edge electric fields, which keeps ∇·B at the cell corners at rounding level. No ψ, no c_h.

7. The field loop got worse with constrained transport

partly fixedct_mhd.jl emf_kernel!, gs05, ecc_kernel!
Problem

Once the CT prototype had its full slope (issue 3), its field loop got worse on finer grids (error of B 0.60, 0.54, 0.88 at 64²–256²). Its edge electric fields are a plain average of the four face fluxes around each edge, which is known to fail this test (Gardiner & Stone 2005). The original's half slope smoothed that away. The new constrained-transport option averages the same way.

Fix

In the CT prototype only: each edge electric field is upwinded by the mass flux through the faces around it (Gardiner & Stone 2005, “CT-contact”), with the cell-centred electric field from the predictor's half-step velocity and the field at the start of the step. New function gs05 and kernel ecc_kernel!; emf_kernel! calls them. In the option, upwinding did not help (0.25 against 0.26 at 128² on the CPU), so it keeps the plain average.

8. PPM blows up at 512²

On the field loop and on Kelvin–Helmholtz with a confined field, the fixed PPM kernel runs to the end, but ψ grows exponentially from t ≈ 1 and the field energy ends 92 and 156 times AthenaK's. The original PPM stopped on both runs (field loop at t = 1.8, Kelvin–Helmholtz at t = 2.7); the fixes removed the crash, not the instability. No other run, original or fixed, ends that far off. open

9. Runs that no longer finish
  • CT prototype, 9 runs: every Mach 9 decay run (64³–512³, two seeds; stops at t ≤ 0.02) and the Mach 2 decay at 512³, seed 1 (t = 0.375). Once second order, the pressure goes negative behind the strongest shocks; the original's first-order diffusion kept it positive. The GLM kernels, with the same slope limiter and HLL speeds, survive the same flow on the CPU, so the CT prototype lacks a safeguard they have, not yet found.
  • CT option, 3 runs: Mach 2 decay, 256³ seed 3 and 512³ seeds 2 and 3, all at t = 0.375.
  • PPM, 2 runs: 2D blast without a field at 32² (t = 0.008) and Kelvin–Helmholtz with a uniform field at 512² (t = 2.9).

open

10. B_z grows with the CT option

On the field loop moving out of the plane (128²), B_z, which only divergence errors can create, reaches 4 × 10⁻² of the loop's field: 6 times the fixed production kernel with GLM (6.5 × 10⁻³). The option does keep the field along the rotated Brio–Wu shock normal to 5 × 10⁻⁵ (GLM 6 × 10⁻⁴). open

Checking the branch against the original

With the switches off (anchored=false, fct=false, no dt_cfl) the branch runs the original code except for the HLLD test of commit 893e82a. Against the sweep's runs of the original:

  • LLF kernel: identical in all 21 outputs × 35 diagnostics, on the entropy wave and Orszag–Tang.
  • Production kernel: identical on the entropy wave.
  • Production kernel on Orszag–Tang, and PPM: not identical but equal to rounding: the same number of steps, total energy within 3 × 10⁻⁸, kinetic and magnetic energy within 3 × 10⁻⁶, shock errors equal to 3 digits. The differences appear only where ψ is not zero, so the GPU compiler arranges some cleaning arithmetic differently in the larger kernel; the sweep's own repeated runs match each other exactly.

What we would recommend

On power-of-two grids, the Float32 4-cell tile: as fast as Float16 there, as accurate as the fixed Float16 kernel up to 256 (less at 512), and it survives Mach 9. On grids divisible by 6, the fixed Float16 6-cell tile is the fastest accurate kernel (1.91 billion per second). Where leakage matters, the fixed CT prototype: it leaks no more than the CT codes (0.9–1.7 times the reference at 64²–512²), is second order and handles the field loop, but it is 4 times slower and stops at Mach 9. Courant 0.25–0.3 in 3D.
